# CPU V0.3 联合集成接口与验证范围

## 使用的正式模块

本次新增 `pipeline_cpu_core_v03.v`，通过实例复用正式 `decoder`、`regfile`、`imm_gen`、`alu`、`if_id_reg`、`id_ex_reg`、`ex_mem_reg`、`mem_wb_reg`、`forwarding_unit`、`load_use_hazard_unit`、`dmem`。既有的 V0.1/V0.2、V0.9 和单周期 CPU27 文件均保持不变。

## 顶层握手和观察信号

| 端口 | 方向 | 位宽 | 含义 |
|---|---|---:|---|
| `clk`, `rst` | 输入 | 1 | 时钟、同步高有效复位 |
| `if_valid`, `if_pc`, `if_inst` | 输入 | 1、32、32 | 外部提供的待取指令 |
| `if_ready` | 输出 | 1 | 为 1 时上升沿接受指令；为 0 时上游保持本条指令 |
| `load_use_stall` | 输出 | 1 | EX 中 Load 目的寄存器被 ID 指令使用 |
| `wb_commit_valid` | 输出 | 1 | 有效寄存器写回（屏蔽 r0） |
| `wb_commit_pc`, `wb_commit_rd`, `wb_commit_data` | 输出 | 32、5、32 | 写回可观察元数据 |
| `mem_store_commit_valid` | 输出 | 1 | 当前 MEM 中 ST.W 将于本上升沿写入数据 RAM |
| `mem_store_commit_pc`, `mem_store_commit_addr`, `mem_store_commit_data` | 输出 | 32、32、32 | Store 写入的 PC、字节地址和写入数据 |
| `id_unsupported`, `id_raw_hazard` | 输出 | 1、1 | 不支持指令与数据相关诊断 |

## 控制不变量

- `load_use_hazard_unit` 发出 `hold_ifid_req` 和 `bubble_idex_req`；ID/EX 的 Flush 优先于 Stall。
- EX 中的旧 Load 必须继续流入 EX/MEM，不能因为年轻指令等待而 Flush 或 Stall EX/MEM。
- `mem_store_commit_valid` 必须受 `mem_valid && mem_mem_write && !rst` 限定，防止 Bubble/Reset 写数据 RAM。
- Store 数据在 EX 阶段使用前递后的源寄存器 B；访存地址使用 ALU `rs1 + sign_extend(si12)`。
- EX/MEM 的 Load 不能把地址当作读取值前递。消费者通过 Bubble 等待，让 Load 值进入 MEM/WB 再前递。
- 当前没有 MEM/WB Stall 或多周期访存反压，因此每个存储事务被接收一次；引入真正下游反压后须设计 per-instruction ready/valid/commit。

## 本版本不覆盖

Branch/Redirect/Flush 协同、多周期 Cache Miss、DMEM 外部总线握手、非对齐或越界异常、中断、完整 27 条指令整机回归。V0.3 的通过不能替代上述验证。

## 测试程序

`load_store_v03.mem` 包含 62 条机器码，起始 PC `0x1000`，共 43 次寄存器写回、16 次 ST.W，2 条预期被过滤的指令；另有写 r0 的算术指令被屏蔽。不变更 ROM 索引来制造暂停，必须等 `if_ready` 恢复再送下一条指令。

最终判定：Testbench 逐笔核验每次 WB 与 Store，并检查 IF/ID 停止、ID/EX Bubble、旧 Load 前进、数据存储器及寄存器堆终值。

## 三、队员 A 应交付的正式 RTL 接口信息

- 文件相对路径、`module` 名、完整端口清单及位宽（不能假定名称等于 v06 参考驱动）。
- `RESET_PC`、时钟、同步高有效复位、Redirect 输入及有效事件定义。
- 与 Adapter 的 IF 侧：`if_req_valid`、`if_req_addr[31:0]`、`if_req_ready`。
- 明确是否控制 `if_resp_valid`、`if_resp_ready` 和 IF/ID 捕获；若由独立连接层处理，确认职责边界。
- 同步握手：`req_fire = if_req_valid && if_req_ready`（不处于 reset/redirect）。
- 请求地址在 `valid && !ready` 时保持稳定；单个事务仅接受一次。
- Redirect 在 Adapter busy/DRAIN 时保存目标直到目标请求被接受，旧地址不会重新发起。
- 与 `id_can_advance`、`ifid_flush`、`redirect` 的时序关系；任何流水线 Stall 不能吞掉重定向事件。
- 独立 Testbench 与结果截图。

## 四、V0.6 → V0.7 最小改动方案

1. 保留 `tb_ifetch_subsystem_v06.v` 作为回归基线，不覆盖。
2. 新建 V0.7 联合连接模块与 `tb_ifetch_subsystem_v07.v`，采用正式 PC/IF 控制器；若端口不同，使用**薄适配连接层**，不要改正式 PC/IF 核心或 Cache/Adapter。
3. 新的 `tb_v07` 不能只依赖 `dut.u_adapter`、`dut.if_resp_inst` 等内部层级路径；必要时导出调试端口，避免依赖实例命名。
4. 首轮保持相同后备 ROM 及延迟设置；运行基线 V0.6，再运行 V0.7。
5. 通过后追加随机 Stall、Redirect 与 Cache Miss 的交叉场景及超时监测。

## 五、V0.7 验收矩阵

| ID | 场景 | 必须满足 |
|---|---|---|
| 01 | 顺序 PC / Hit、Miss | PC 按 4 推进；有效指令不重不漏；单未完成请求 |
| 02 | Miss 时 ID Stall | 响应保持，Stall 解除后仅消费一次 |
| 03 | 已返回响应时 Stall | 响应 PC/指令/错误位稳定，握手为 0 |
| 04 | Miss 期间 Redirect | 旧请求安全排空；错误路径不交付；目标 PC 必须完成取指 |
| 05 | Cache ready 同周期 Redirect | 不泄漏旧响应；优先取新目标 |
| 06 | Stall + Redirect + Flush | Flush 有效，旧响应不消费，新目标不丢失 |
| 07 | Reset + Stall + Flush | IF/ID 有效位清零，请求状态复位 |
| 08 | 多次 Redirect | 明确是否支持；不支持时形式化约束并测试受限行为 |
| 09 | 错误取指 | 错误响应不作为正常指令进入 ID |
| 10 | 长时间 busy/backpressure | 无组合握手环、死锁或重复 req_fire |

## 六、重点自检：不能把测试参考驱动当成正式控制器

`if_pc_driver_v06.v` 中 `if_req_valid = !rst && !redirect`，它只依赖 Adapter 单未完成请求机制，不代表队员 A 最终的 PC 控制实现。V0.6 的通过不能直接作为 V0.7 正式 PC RTL 的通过证明。
